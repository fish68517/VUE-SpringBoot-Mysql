# 在线投稿系统需求实现审核报告

审核日期：2026-05-01

审核范围：`需求/需求.md`、`SpringBoot` 后端、`VUE` 前端、`SpringBoot/src/main/resources/db/schema.sql`、`交付/submission_system*.sql`。

## 一、总体结论

当前项目已经搭建出“作者、编辑、审稿人、系统管理员”四类角色的基本页面、路由、控制器、服务、Mapper 和数据库表，页面数量和接口数量基本覆盖了需求描述的大部分模块。

但从“小验”角度看，系统还不能认定为完整实现需求，主要原因如下：

1. 多数业务接口存在前后端路径不一致风险，后端 `server.servlet.context-path` 配置为 `/api`，但大部分控制器又以 `/api/...` 开头，真实路径会变成 `/api/api/...`，而前端大部分请求仍是 `/api/...`。
2. 注册审批流程没有闭环，后端注册时直接将用户设为 `ACTIVE`，管理员审批逻辑却只审核 `PENDING` 用户，导致“审核编辑、审稿人注册信息”功能实际不可用。
3. 稿件终审流程缺失，审稿人提交审稿意见后，稿件状态没有根据审稿结论流转为 `ACCEPTED`、`REJECTED` 或 `REVISION_REQUIRED`，所以“终审通过后编辑排版、生成录用通知”流程基本不可达。
4. 作者退修流程不合理，稿件进入 `REVISION_REQUIRED` 后，后端不允许作者修改和重新上传文件，前端也禁用了该状态下的编辑按钮。
5. 前端存在明确的运行时缺口，例如编辑沟通页面调用 `editorService.getAllAuthors()`，但 `editorService.js` 未定义该方法，后端也没有对应 `/editors/authors` 接口。
6. 数据库外键没有按需求统一设置 `ON DELETE CASCADE`，交付 SQL 中多数外键仍为 `ON DELETE RESTRICT`，资源 SQL 中多数外键未声明级联删除。
7. 后端测试未通过，前端构建因为依赖未安装无法完成验证。

结论：系统具备毕业设计展示的雏形，但目前只能算“部分实现”。如果用于演示，需要先修复接口路径、用户审批、终审状态流转、退修重投、编辑沟通、数据库级联约束等核心问题。

## 三、关键缺陷和流程不合理点

### 1. 接口路径存在系统性不一致

后端配置：

```yaml
server:
  servlet:
    context-path: /api
```

同时多数控制器声明：

```java
@RequestMapping("/api/manuscripts")
@RequestMapping("/api/editors")
@RequestMapping("/api/reviewers")
```

这会让真实接口变成 `/api/api/manuscripts`、`/api/api/editors`、`/api/api/reviewers`。但前端服务大多请求 `/api/manuscripts`、`/api/editors`、`/api/reviewers`。登录注册接口比较特殊，`AuthController` 是 `/auth`，配合 context-path 后真实路径是 `/api/auth`，前端刚好可用。

建议二选一统一：

1. 保留 `context-path: /api`，所有控制器去掉路径前缀里的 `/api`。
2. 删除 `context-path: /api`，所有控制器保留 `/api/...`。

不建议继续混用，否则页面会出现“登录成功，但进入业务页面接口 404”的问题。

### 2. 注册审批流程和需求相冲突

需求要求管理员审核编辑、审稿人注册信息。当前 `UserService.register()` 注释写的是创建 `PENDING` 用户，但实际代码设置为：

```java
.status("ACTIVE")
```

而 `UserManagementService.approveUser()`、`rejectUser()` 只允许处理 `PENDING` 用户。结果是新注册用户不会进入审批列表，管理员审批功能无法验证。

建议：

1. 作者可直接 `ACTIVE`，编辑和审稿人注册为 `PENDING`。
2. 登录时限制 `PENDING/REJECTED/INACTIVE` 用户进入系统。
3. 审批通过后状态统一改为 `ACTIVE`，不要同时混用 `APPROVED` 和 `ACTIVE`，否则 `findAllActiveReviewers()` 只查 `ACTIVE` 会漏掉 `APPROVED` 审稿人。

### 3. 终审状态流转缺失

审稿人提交意见后，`ReviewerService.submitReviewOpinion()` 只把 `reviews.status` 改为 `SUBMITTED`，并保存 `recommendation`，但没有更新 `manuscripts.status`。

因此以下需求无法闭环：

1. 审稿意见“同意录用 / 修改后录用 / 拒绝录用”不会转化为稿件最终状态。
2. 编辑端 `getAcceptedManuscripts()` 查询 `ACCEPTED` 稿件，但系统没有正常路径把稿件置为 `ACCEPTED`。
3. 编辑“终审通过后格式排版、内容校对、生成录用通知”入口可能长期为空。
4. 管理员通过率统计依赖 `ACCEPTED/REJECTED`，但这些状态很难自然产生。

建议新增编辑终审决策接口，例如：

```text
POST /editors/manuscripts/{id}/final-review
```

由编辑查看审稿意见后选择 `ACCEPTED`、`REVISION_REQUIRED`、`REJECTED`，同时向作者发送最终通知。

### 4. 作者退修重投流程被阻断

需求要求作者接收退修通知并上传修改后的稿件。但当前后端只允许 `DRAFT` 或 `SUBMITTED` 状态修改：

```java
if (!"DRAFT".equals(existingManuscript.getStatus()) && !"SUBMITTED".equals(existingManuscript.getStatus())) {
    throw new RuntimeException("Only manuscripts in DRAFT or SUBMITTED status can be modified");
}
```

前端作者稿件列表也禁用了 `REVISION_REQUIRED` 状态下的编辑按钮。结果是编辑退修后，作者反而不能上传修改稿。

建议：

1. 后端允许 `REVISION_REQUIRED` 修改。
2. 修改提交后状态改回 `SUBMITTED` 或 `UNDER_REVIEW`，取决于是否需要重新初审。
3. 前端按钮文案区分“修改”和“上传修改稿”。
4. 保留初审/审稿意见历史，避免覆盖前一轮意见。

### 5. 编辑沟通页面存在缺失接口

`VUE/src/views/editor/Communication.vue` 调用：

```js
editorService.getAllAuthors()
```

但 `VUE/src/services/editorService.js` 中没有该方法，后端 `EditorController` 也没有 `/authors` 接口。该页面加载作者列表时会直接运行时报错。

建议直接复用已有 `userService.getUsersByRole('AUTHOR')`，或者在 `editorService` 和后端补齐 `getAllAuthors()`。

### 6. 数据库级联删除不符合需求

需求明确要求外键为 `ON DELETE CASCADE`。当前：

1. `SpringBoot/src/main/resources/db/schema.sql` 的外键大多没有声明 `ON DELETE CASCADE`。
2. `交付/submission_system.sql` 和 `submission_system_scheml.sql` 中多数外键是 `ON DELETE RESTRICT`。
3. 只有 `messages.manuscript_id` 在交付 SQL 中是 `ON DELETE CASCADE`。

这会造成管理员删除用户、栏目、稿件时可能因外键约束失败。尤其删除已有投稿的作者、已有审稿任务的审稿人、已有稿件的栏目，都存在失败风险。

建议将需求中的级联策略落实到所有相关表，至少包括：

1. `manuscripts.author_id -> users.id`
2. `manuscripts.category_id -> categories.id`
3. `initial_reviews.manuscript_id -> manuscripts.id`
4. `reviews.manuscript_id -> manuscripts.id`
5. `reviews.reviewer_id/editor_id -> users.id`
6. `messages.sender_id/recipient_id/manuscript_id`

同时要注意：用户删除是否真的应该级联删除所有投稿和消息，是业务策略问题。需求要求级联删除，但实际系统展示时也可以考虑改成禁用用户，避免数据丢失。

### 7. 系统管理员账号缺少初始化数据

注册页面只允许作者、编辑、审稿人注册，没有管理员注册入口。交付 SQL 中也未发现 `ADMIN` 用户初始化记录。这意味着新环境导入数据库后，管理员可能无法登录，进而无法审核用户、维护栏目和系统配置。

建议在初始化 SQL 中提供一个默认管理员账号，例如：

```sql
INSERT INTO users (username, password, role, status) VALUES ('admin', '123456', 'ADMIN', 'ACTIVE');
```

### 8. 审稿任务状态语义混用

`reviews.status` 同时用于表示任务状态：

1. `PENDING`：待接受
2. `ACCEPTED`：审稿人已接受任务
3. `REJECTED`：审稿人拒绝任务
4. `SUBMITTED`：已提交审稿意见

而审稿意见中的拒稿结论存放在 `recommendation=REJECT`。这种设计可运行，但容易在页面和统计中混淆“审稿人拒绝任务”和“审稿人建议拒稿”。

建议：

1. 任务状态继续使用 `PENDING/ACCEPTED/DECLINED/SUBMITTED`。
2. 审稿结论使用 `recommendation=ACCEPT/ACCEPT_WITH_REVISION/REJECT`。
3. 不要把任务拒绝写成 `reviews.status=REJECTED`，避免和稿件拒稿混淆。

### 9. 前端请求方式不统一

大部分服务使用封装后的 `api`，但审稿人部分页面仍存在原生 `axios` 和 `/api/api/...` 写死路径，例如：

1. `VUE/src/views/reviewer/History.vue`
2. `VUE/src/views/reviewer/Tasks.vue`

这会绕过统一错误处理和 `withCredentials` 配置，Session 场景下可能出现未登录、路径错误或跨域问题。

建议统一改为 `src/services/api.js`，并统一路径规则。

### 10. 文件删除路径存在小问题

上传时 `FileUploadUtil.uploadFile()` 返回 `image/xxx` 或 `image\xxx`，提交时又手动去掉了 `image\`。但删除旧文件时直接：

```java
Path path = Paths.get(filePath);
```

如果数据库只保存 `xxx.pdf`，删除时会尝试删除项目根目录下的 `xxx.pdf`，而不是 `image/xxx.pdf`。这会导致旧文件残留。

建议数据库统一只保存文件名，删除和访问时都显式拼接 `image` 目录。

## 四、技术要求检查

### 已符合或基本符合

1. 后端使用 Spring Boot 3.x，前端使用 Vue 3。
2. 使用 MySQL、MyBatis、Vue Router、Pinia、Axios、Element Plus。
3. 未引入 Spring Security、JWT、Sa-Token 等权限框架。
4. 密码为明文保存和校验，符合需求中的简化要求。
5. 文件上传保存到 `image` 目录，数据库保存路径/文件名。
6. 有全局 CORS 配置。
7. 有作者顶部导航布局、管理员/编辑/审稿人侧边栏布局。
8. 登录后按角色跳转。

### 未符合或需要修正

1. 外键未按需求统一 `ON DELETE CASCADE`。
2. `/image/**` 理论映射存在，但因 `context-path=/api`，实际访问路径不是根路径 `/image/**`。
3. 代码注释、调试日志和接口返回文本大量仍是英文，不满足“页面所有文本、代码注释和调试日志采用中文简体”的要求。
4. 系统日志管理没有页面和接口，仅有 Spring Boot 日志配置。
5. 系统配置目前是 CRUD，没有真正控制审核流程。

## 五、验证结果

### 后端测试

执行命令：

```bash
mvn test
```

结果：后端编译通过，但测试失败。

失败点：

1. `UserServiceTest.testRegisterNewUser`：期望注册用户状态为 `PENDING`，实际为 `ACTIVE`。
2. `UserServiceTest.testLoginUserNotApproved`：期望未审批用户不能登录，实际未抛异常。
3. `EditorServiceTest.testAssignReviewerSuccess`：测试中 `NotificationService` 未注入，分配审稿人发送通知时空指针。

这些失败与前文发现的“审批流程不一致”和“服务依赖测试未同步”相吻合。

### 前端构建

执行命令：

```bash
npm.cmd run build
```

结果：构建未完成，原因是当前工作区没有安装前端依赖，报错为找不到 `vite` 包。

说明：这不是业务代码一定无法构建，但当前环境无法完成前端构建验证。需要先执行 `npm install` 或 `npm ci` 后再验证。

## 六、整改优先级建议

### 必须优先修复

1. 统一接口路径，解决 `/api` 和 `/api/api` 混乱。
2. 修复注册审批流程：编辑、审稿人注册为 `PENDING`，审批通过后可登录。
3. 补齐管理员初始化账号。
4. 补齐终审决策流程，使稿件能从审稿意见流转到 `ACCEPTED/REJECTED/REVISION_REQUIRED`。
5. 修复作者退修后不能修改的问题。
6. 补齐编辑沟通页面作者列表接口或改用现有用户接口。

### 小验前建议修复

1. 将前端所有请求统一走 `api.js`。
2. 修复数据库外键 `ON DELETE CASCADE`，或明确改为逻辑删除并同步说明。
3. 修复文件删除路径，避免上传文件残留。
4. 安装前端依赖并完成一次 `npm run build`。
5. 修复后端测试用例或实现，使 `mvn test` 通过。

### 展示效果优化

1. 将英文注释、接口提示和 `System.out.println` 调试日志改为中文或正式日志。
2. 系统配置页面增加“审核流程配置”的实际使用说明，避免看起来只是字典维护。
3. 统计报表可导出为 Excel 或 CSV，比 JSON 更适合本科毕设展示。
4. 作者端增加“草稿保存”功能，否则 `DRAFT` 状态在正常投稿流程中几乎不会出现。

## 七、最终判断

当前系统不是“完整实现需求”，而是“页面和接口框架基本齐全，但核心业务闭环未完全打通”。

如果只做静态演示，作者投稿、编辑初审、分配审稿、审稿人提交意见、消息查看等部分可以展示；如果按需求完整验收，用户审批、终审录用/拒稿、退修重投、编辑沟通、数据库级联删除、接口路径一致性必须修复。
