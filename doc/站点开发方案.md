# 防汛预警站点扩展开发方案

> 版本：V1.0
>
> 日期：2026-09-11
>
> 目标页面：`http://127.0.0.1:8085/waterlog-dia-bus`
>
> 当前状态：已按本方案完成代码实施；默认使用 mock 数据，开发编译和页面交互验收通过，真实接口联调待切换开关后验证。

## 1. 需求落地结论

本次采用“一个静态双 Tab 标题 + 一个两江合并站点列表 + 一套统一预警计算链路”的增量方案：

1. 在当前“嘉陵江”标签右侧增加“长江”标签，两者尺寸、圆角、间距和背景结构一致；嘉陵江使用现有蓝色，长江文字使用降雨量标题的橙黄色系；
2. 嘉陵江保持唯一激活项，长江标签仅用于视觉表达，不触发切换、不清空数据、不重新请求接口；
3. 嘉陵江标签下方的滚动列表同时显示嘉陵江、长江到朝天门的业务站点，并按河道传播顺序排列；
4. 使用“获取所有站点水情综合信息”接口一次取得站点、坐标、距离、实时水位、警戒水位和保证水位，禁止逐站请求造成 N+1 调用；
5. 将接口原始字段统一适配为现有 `Station`，所有站点继续复用同一个输入锁定、地图标记、预警计算和结果展示逻辑；
6. 增加默认开启的 mock 开关。mock 数据结构模拟真实接口，而不是直接伪造组件内部状态，从而同时覆盖接口适配层；
7. 接口或 mock 返回有效阈值后，化龙桥、大溪沟、千厮门、塔坪、钓二嘴等站点自动取消灰态并允许输入；真实接口仍缺阈值时不伪造生产数据，保留灰态并记录缺失原因。

## 2. 现状分析

### 2.1 当前实现位置

主组件：

`src/package/BZAQ/BzWaterKpiDia/components/WaterlogPredictionDia.vue`

当前站点、河道和算法分别位于：

- `components/flood-data.ts`：15 个本地静态站点、嘉陵江和长江线路；
- `components/flood-engine.ts`：嘉陵江、长江及两江联合预警规则；
- `WaterlogPredictionDia.vue`：右侧列表、单站输入、地图标记、计算按钮和告警结果。

长江站点实际上已经存在于 `STATIONS`，长江预警规则也已经存在；目前看不到长江站点，是因为 `stationGroups` 中的长江分组被注释。因而本次不重写算法，只补齐数据加载、合并显示、名称标准化和状态同步。

### 2.2 当前需要同时修正的关联问题

1. 站点置灰只判断 `warning == null`，输入禁用却只判断是否为朝天门/郭家沱；应统一为“必须有警戒和保证阈值且不是非触发站点”；
2. 已存在 `isInputDisabled()` 单站锁定函数，但模板没有使用它。实施时应改为 `!isTrigger(s) || isInputDisabled(s.name)`，保证输入一个站点后其他可触发站点锁定；
3. `resetStaticData()` 当前会重新复制原始 `STATIONS`，会丢掉刚加载的接口/mock 阈值；应改为恢复“本次加载成功后的快照”；
4. 接口常见名称可能是 `北碚(三)`、`泸州(三)`，本地展示名是 `北碚（三）`、`泸州（三）`，如果不做别名归一会合并失败；
5. 现有提示语写死了“无数据站点”名单。接口补齐后必须改成根据当前数据动态生成，不能继续显示过期说明。

## 3. Tab 与站点列表设计

### 3.1 静态 Tab 语义

```html
<div class="river-tabs" role="tablist" aria-label="河流站点">
  <button class="river-tab river-tab--jialing is-active" role="tab" aria-selected="true">
    嘉陵江
  </button>
  <span class="river-tab river-tab--yangtze" role="tab" aria-disabled="true">
    长江
  </span>
</div>
```

- 嘉陵江：沿用 `#2196F3` 蓝色和现有标签样式；
- 长江：背景结构与嘉陵江相同，文字/描边使用降雨量标题当前使用的 `#FFB13B`—`#FF9800` 橙黄色；
- 长江不绑定 `@click`，不创建 `activeRiver`，避免形成“看似可切换但没有内容”的伪交互；
- 两个标签下方只有一套站点列表和滚动条，不改变右侧栏其他表单布局。

### 3.2 合并列表顺序

用固定业务顺序控制展示，接口仅补数据，不能让接口返回顺序改变洪水传播顺序：

```ts
const DISPLAY_ROUTE_ORDER = [
  '鸭嘴', '东津沱', '北碚（三）', '磁器口', '化龙桥', '大溪沟', '千厮门',
  '泸州（三）', '塔坪', '钓二嘴', '李家沱', '菜园坝', '玄坛庙',
  '朝天门', '郭家沱'
] as const
```

规则：

- 朝天门是两江共享汇合站，只显示一次；
- 郭家沱位于朝天门下游，保留现有展示，但继续作为非触发站点；
- 接口返回的其他重庆水文站不自动加入此业务列表，避免把全市站点全部塞入 360px 侧栏；
- 列表高度继续使用当前固定高度和内部滚动，不挤压放水量、降雨量、按钮和告警结果。

## 4. 接口方案

### 4.1 主接口

接口文档中的主加载接口：

```text
POST /api/boot/system/common/getAllHydrologyStationInfo
Content-Type: application/x-www-form-urlencoded（文档定义）
Authorization: 可选
请求体：无
响应列表：data.stations
```

项目已有可复用地址：

```ts
const HYDROLOGY_BASE_URL = 'http://23.210.227.34:23343/yzqzlzx'
const ALL_STATION_URL = `${HYDROLOGY_BASE_URL}/api/boot/system/common/getAllHydrologyStationInfo`
```

`BzWaterRiskDevice/index.vue` 和 `WaterlogPerceptionDeviceList.vue` 已采用 `axios.post(ALL_STATION_URL)` 并读取 `res.data.data.stations`，本组件按该方式保持一致。

### 4.2 本次不作为主加载接口的接口

`POST /api/boot/system/common/getHydrologyStationInfo` 支持 `stcd/stnm/startTime/endTime`，并返回 `stationDetail + historyList`，适合站点详情和历史曲线。当前右侧列表只需站点基础信息与阈值，而 `getAllHydrologyStationInfo` 已包含所需字段，因此本次不对 15 个站点逐个调用详情接口。

后续若产品增加站点历史曲线，可在用户点击某站点时按需调用详情接口并做缓存，不能在弹窗初始化时批量调用。

### 4.3 请求约束

- 默认 mock 模式下不发送网络请求；
- API 模式超时建议 10 秒；
- 不在源码硬编码 Authorization，沿用宿主 axios 默认请求头；若宿主未注入 token，按接口文档的可选 token 行为请求；
- HTTP 2xx 后仍必须校验 `data.stations` 为数组，不能只根据 `code` 字段判断，因为文档未定义成功 code 的固定值；
- 请求失败时保留现有基线站点并显示/记录“接口加载失败”，不能把所有站点清空；
- 组件卸载后忽略迟到响应，防止关闭弹窗后继续重建地图。

## 5. 数据模型与字段适配

### 5.1 组件统一模型

在不破坏现有算法字段的前提下扩展 `Station`：

```ts
export interface Station {
  name: string
  river: '嘉陵江' | '长江'
  lon: number
  lat: number
  dist: number
  warning: number | null
  guarantee: number | null
  z?: number | null
  stcd?: string
  source?: 'base' | 'mock' | 'api'
  missingFields?: string[]
}
```

### 5.2 接口字段映射

| 组件字段 | 接口字段优先级 | 规则 |
| --- | --- | --- |
| `name` | `stnmShort` → `stnm` | 去空格、半角括号转全角，再经过别名表 |
| `stcd` | `stcd` → `reqStcd` | 保留字符串，不转数字 |
| `river` | `rvnm` → `hlname` → `hnnm` | 接口缺失时使用基线站点河流 |
| `lon` | `lon` → `lgtd` | 必须是有效经度；无效时使用基线坐标 |
| `lat` | `lat` → `lttd` | 必须是有效纬度；无效时使用基线坐标 |
| `dist` | `dist` → `distance` | `0` 对朝天门有效，不能用 `||` 丢弃 |
| `warning` | `ivhz` → `wrz` → `ogrsw` → `taz` | 只接收有限正数；空串和示例占位 `0` 视为缺失 |
| `guarantee` | `grz` | 只接收有限正数 |
| `z` | `z` → `sw` | 当前水位仅用于显示，不自动作为用户的预警试算输入 |

名称别名至少包含：

```ts
const STATION_NAME_ALIASES: Record<string, string> = {
  '北碚(三)': '北碚（三）',
  '泸州(三)': '泸州（三）'
}
```

合并策略为“基线定义控制名称、河流、顺序和坐标兜底；接口/mock 覆盖 `stcd/dist/warning/guarantee/z`”。这样接口缺字段时地图仍能定位，同时不会把接口中的空串或 0 覆盖成有效阈值。

## 6. Mock 数据设计

### 6.1 开关

新增独立数据文件并默认使用 mock：

```ts
export const USE_STATION_MOCK = true
```

行为：

- `true`：直接返回 `MOCK_ALL_HYDROLOGY_RESPONSE.data.stations`，不发请求；
- `false`：调用真实接口；接口失败时保留 `STATIONS` 基线数据并进入 error 状态，不静默伪装成接口成功；
- mock 和 API 必须经过同一个 `normalizeAndMergeStations()`，避免出现“两套业务逻辑”。

## 7. 组件数据流

```text
组件 mounted
  → loadHydrologyStations()
      → USE_STATION_MOCK ? 读取 mock : POST 全站接口
      → 校验 data.stations
      → 名称归一化 + 业务站点白名单过滤
      → 与 STATIONS 基线合并并按 DISPLAY_ROUTE_ORDER 排序
      → 保存 loadedStationSnapshot
  → 初始化 levels（所有可触发站点为 0）
  → 初始化 Leaflet 地图、站点 marker、图表和粒子
  → 用户输入任一站点
      → lockedStation 锁定其他站点
      → 点击“计算预警”
      → evaluateWarning(当前完整站点列表, levels)
      → 更新告警结果、站点高亮和告警路径
```

API 模式返回后不应在已有 Leaflet 实例上反复追加 marker。推荐先完成站点数据加载再调用 `initMap()`；若未来需要轮询，则必须实现 `clearStationLayers() + rebuildStationLayers()`，不能重复创建同名图层。

## 8. 预警计算兼容方案

`flood-engine.ts` 已包含长江规则：泸州（三）、塔坪、钓二嘴、李家沱、菜园坝、玄坛庙，以及两江联合规则。本次应保持规则含义不变，只保证输入名称在进入算法前已标准化。

触发资格调整为：

```ts
function isTrigger(station: Station) {
  const isExcluded = station.name === '朝天门' || station.name === '郭家沱'
  return !isExcluded && station.warning != null && station.guarantee != null
}
```

因此：

- mock 模式下所有原灰态业务站点获得阈值并可输入；
- API 模式下只有真实返回有效阈值的站点取消灰态；
- 朝天门继续作为目标站显示当前水位，不作为上游触发输入；
- 郭家沱继续用于出境距离语义，不作为朝天门上游预警触发输入；
- 手工输入值仍存放在 `levels`，接口的实时水位 `z/sw` 不自动参与模拟计算，避免打开页面就意外触发预警。

## 11. 测试与验收

### 11.1 Mock 模式

1. Network 中不出现水情接口请求；
2. 嘉陵江与长江标签并排，长江为橙黄色且点击无状态变化；
3. 列表显示 15 个去重站点，朝天门只出现一次；
4. 化龙桥、大溪沟、千厮门、塔坪、钓二嘴不再置灰；
5. 输入任意长江站点后，其他站点锁定；清零后解除锁定；
6. 用泸州（三）、塔坪、钓二嘴等数据可命中长江规则；
7. 用一条嘉陵江数据和一条长江数据可命中两江联合规则；
8. 重置后站点阈值仍来自 mock，不退回旧的 `null`。

### 11.2 API 模式

1. 初始化只调用一次 `getAllHydrologyStationInfo`；
2. 正确兼容半角/全角括号站名；
3. 空字符串、`NaN`、占位 0 不被当作有效阈值；
4. 接口额外站点不会进入业务列表；
5. 有效阈值覆盖基线值，缺失字段使用基线兜底；
6. 接口失败、超时或响应结构错误时页面仍可打开，基线站点和地图不消失；
7. 未从真实接口获得阈值的站点保持灰态，不使用 mock 阈值冒充真实值。

### 11.3 回归与工程检查

1. 嘉陵江原有输入、计算、告警动画和地图高亮不变；
2. 草街放水量、降雨量、告警结果和粒子开关不受影响；
3. 右侧 360px 布局不横向溢出，合并列表只在自身区域垂直滚动；
4. Vue/TypeScript/SCSS 开发编译通过，`git diff --check` 通过；
5. mock 与 API 各验证一次蓝、黄、红和无预警场景；
6. 组件关闭后无迟到请求导致的 DOM、Leaflet 或 ECharts 更新。

## 12. 风险边界

- 接口文档只给出字段结构，没有提供真实站点样例、站点编码和成功 code；正式联调必须以实际返回为准，不能把本方案中的 `MOCK-*` 编码或模拟阈值提交给生产接口；
- 文档同时提供 `ivhz/wrz/ogrsw/taz` 多个“警戒水位”字段，当前项目既有实现优先 `ivhz`、再取 `wrz`。本方案保持这一顺序，并仅把其他字段作为兼容兜底；
- 如果真实接口的 `lon/lat` 坐标基准与当前高德瓦片不一致，需要单独确认 WGS84/GCJ-02，不能在站点适配层盲目重复转换；
- `getAllHydrologyStationInfo` 可能返回大量站点，因此必须使用固定白名单和别名映射，不能按河名模糊匹配后全部展示；
- 是否允许朝天门作为手工输入触发站点属于预警业务规则变更，本次按现有逻辑继续禁用，不在 UI 需求中擅自改变。

## 13. 最终实施判定

该方案无需新增后端接口，也无需修改现有预警算法主体。工程落地的关键是把接口/mock 数据统一收敛为现有 `Station`，并让地图、列表和算法始终消费同一份 `stationList`。默认 mock 可以立即完成 UI 和计算联调；切换为 API 后，只要接口为目标站点返回有效警戒/保证水位，原灰态站点即可自动转为可输入并参与计算。
