# 来电显示信息未正确采集：bug 分析

分析日期：2026-09-29。

> 后续状态：已按本报告实施源码修复及历史记录功能，见 [修复实现说明](修复实现说明.md)。下文保留修复前的分析和实验结果；其中“未实施”、旧行号及旧探针结果描述的是修复前状态，不是当前实现。

分析对象：用户提供的两张截图，以及本目录下 `来电标记采集助手_Kotlin_Android14-16_完整项目/CallMarkCollector` 的当前源码。本次只增加分析文档与本地验证材料，未修改 Android 业务代码、安装应用或重新打包 APK。

## 1. 结论

**现有代码有能力解析例图1中的文字，但采集链路不能保证拿到的就是来电窗口文字。最值得优先排查的是：扫描了错误窗口，随后宽松的解析规则把采集助手自身页面当成来电信息。**

已直接编译并运行当前 `CallScreenParser.kt` 和 `ParsedCallInfo.kt`，得到两组关键结果：

| 输入文字 | 当前解析器实际输出 |
| --- | --- |
| `移动 来电`、`16人标记`、`广告推销`、`广东东莞 0769 2173 8692` | 号码 `076921738692`，已标记，人数 `16`，类型 `广告推销` |
| `来电标记采集助手`、`12123` | 号码 `12123`，已标记，人数 `null`，类型 `来电采集助手` |

第二组**复现了例图2错误记录中的四个业务字段**。它证明存在可触发的解析缺陷，但不证明手机当时实际读到的节点就是这两个字符串；`12123` 的原始来源仍需日志确认。来源应用 `unknown` 属于服务层赋值问题，不是上述解析器产生的字段。

因此，不能只归因于“手机不给无障碍权限”，也不能只增加“广告推销”关键词——当前词库已经包含它。应先修正窗口选择、来源校验、解析兜底和会话补全，再根据真机节点情况适配。

### 2.2 例图2并不是同一种窗口形态

例图2里，采集助手页面在下方，来电卡片悬浮在上方。肉眼同时看得到两者，并不意味着它们属于同一个无障碍根节点。

悬浮卡片可见号码和 `广告推销`，**没有可见的 `16人标记`**。如果实际只拿到了这张卡片的文字，人数只能是未知；除非同次来电之前已读到全屏页面的人数，否则不能从截图推算出 `16`。

下方“最近一次采集”显示 `12123 / 是 / 无 / 来电采集助手 / unknown`，这显然不对应上方来电卡片。`MainActivity.showLastCapture()` 读取的是持久化的最后一条记录，并非实时展示当前来电扫描结果。因此还存在两种需要区分的情况：本次生成了错误记录，或者本次没有成功采集，页面继续显示先前的错误记录。仅凭同一分钟的截图不能排除后一种。

截图中的标题和输入框存在重叠，但这是另一个页面布局现象，不能用来解释号码识别错误。本次不展开修改界面。

## 3. 为什么“画面有字”不等于“无障碍一定能读到”

当前实现通过 `AccessibilityNodeInfo.text` 和 `contentDescription` 读取控件提供的语义内容，没有执行截图 OCR。屏幕像素、事件携带的文本、窗口节点树，是三个不同的数据来源。

Android 官方说明：`rootInActiveWindow` 返回当前活动窗口的根；活动窗口通常与触摸或输入焦点相关。它不会自动拼接所有可见窗口。`getWindows()` 可访问符合条件的交互窗口，但也不等于所有屏幕图层。[官方窗口 API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#getRootInActiveWindow())、[getWindows 说明](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#getWindows())。

所以，无障碍能够识别的前提是：服务正常连接、收到或主动触发了扫描、选中了目标窗口、目标页面向该服务暴露文字节点，而且解析与会话保存没有把结果弄错。当前代码在多个环节都有缺口。

## 4. 当前源码已确认的问题

以下行号以本次检查时源码为准。服务文件简称 `CallerMarkAccessibilityService.kt`，解析器简称 `CallScreenParser.kt`，均位于 `app/src/main/java/com/example/callmarkcollector/` 下的相应包目录。

### 4.1 高优先级：只读活动窗口，没有读取来电所在的其他窗口

位置：服务第 68–80 行。

```kotlin
val root = rootInActiveWindow
collectVisibleText(root, lines, 0)
val parsed = CallScreenParser.parse(textLines)
```

配置文件已经声明 `flagRetrieveInteractiveWindows`，但服务没有遍历 `windows`，也没有使用 `event.windowId` 定位对应窗口，未从 `event.source` 获取候选内容。

在例图2这种“自己的应用 + 来电卡片”场景中，延迟扫描时的活动窗口可能仍是采集助手，也可能已经切换。来电卡片位于哪个包、哪个窗口，必须从真机日志获取，不能仅凭外观认定一定属于 SystemUI 或某个品牌拨号应用。

**缺陷已确认；本次截图是否确实读错根节点，待真机确认。**

### 4.2 高优先级：只过滤自身事件，没有过滤扫描到的自身窗口

位置：服务第 44–60、63–80 行。

代码确实有：

```kotlin
if (packageName == this.packageName) return
```

但它只排除“由本应用发出的事件”。随后程序等待 650ms 才读取 `rootInActiveWindow`，读取时没有再检查 `root.packageName`，也没有把根的窗口 ID 与触发事件对应起来。

可能发生的过程是：

1. 电话应用或系统窗口产生事件，或者响铃期间收到其他应用事件。
2. 服务把事件包名记到 `pendingPackage`，安排延迟扫描。
3. 扫描执行时，活动窗口已变成采集助手页面。
4. 采集助手标题、说明和旧记录被当成来电文本送入解析器。

尤其是 `isRinging == true` 时，第 50 行允许所有非自身包的事件进入，不再要求它们通过来电界面特征判断；“正在响铃”被当成了过宽的扫描许可。

这能解释为什么即使过滤了自身事件，仍可能读到自身标题。

### 4.3 已复现：标记类型兜底把应用标题当成标记类型

位置：解析器第 81–95 行，以及第 33 行。

在没有命中已知标签时，只要一行包含 `标记` 或 `举报`，就删除这些词，再把剩下的 2–24 个含字母字符当成类型。Kotlin 的 `isLetter()` 也会把中文识别为字母类别字符。

于是：

```text
来电标记采集助手 → 删除“标记” → 来电采集助手
```

随后 `markType != null` 又直接使 `isMarked = true`。这与例图2错误的类型和“是否标记：是”高度吻合。

还有一个反向证据：`广告推销` 本来就在词库中，并且已知标签匹配先于兜底。如果同一次解析输入完整包含 `广告推销`，当前代码通常会先返回该类型，不会退到 `来电采集助手`。这进一步提示：生成错误记录的那次输入没有拿到卡片里的这一行，或界面显示的是旧结果。

### 4.4 已复现：号码提取缺少来电区域约束，旧记录和普通数字可入选

位置：解析器第 44–67 行。

实现会从任意文本里找 5–15 位数字候选并打分，没有号码节点、来电区域或来源可信度校验，也没有最低分淘汰条件。

`12123` 是五位数字，可以成为候选；这不意味着短号码本身不合法，问题在于缺少“它来自本次来电号码区域”的证据。当前代码不会凭空生成 `12123`；它必须来自某次解析输入，或已经保存的历史记录。截图无法确定首次来源。

本次另一个合成输入同时包含：

```text
号码：12123
0769 2173 8692 广东…
广告推销
```

实际结果选中 `12123`，因为带“号码”二字的旧记录行获得加分，而混有归属地的座机行没有纯号码行加分。号码和类型还可能被错误地从不同区域拼成一条记录。

另外，模拟 SIM 卡序号和号码处于同一节点：`1 0769 2173 8692`，会得到错误号码 `1076921738692`。这是节点合并时的潜在问题，不能据截图断言手机实际这样暴露节点。

### 4.5 已确认：记录来源保存的是事件包名，不是实际文本来源

位置：服务第 54、119 行。

`sourcePackage = pendingPackage`，后者来自最近一次候选事件；事件包名为空时被设置为 `unknown`。窗口扫描与事件之间有延迟，期间还可能收到别的事件。

因此 `unknown` 不能直接解释为“电话应用隐藏了包名”。它更直接说明记录没有绑定到实际根节点的来源。应分别记录触发事件包名、目标窗口 ID 和实际根节点包名，正式来源取经过校验的内容来源。

### 4.6 已确认：人数缺失仍可立即结束采集，后续不会补全

位置：服务第 101–110、122 行。

只在 `!parsed.isMarked` 时等待更多扫描。只要看到了 `广告推销`，`isMarked` 就已经是 `true`；即使 `markCount == null`，也会立即保存并设置 `sessionUploaded = true`。

之后同一号码再次解析到 `16人标记`，仍会被“已采集”判断拦住。若先读到悬浮卡片、后读到全屏页面，就可能永久保留缺人数的早期结果。标题误判也会触发相同的过早结束行为。

应把“已有候选结果”“字段是否完整”“是否已上传”分开，在有界等待期内合并同一次来电的可信字段；超时仍读不到人数就保留 `null`，不能填零或猜测人数。

### 4.7 已确认：重试和事件时序可能造成漏扫

位置：服务第 63–72、81–86、180–197、218–221 行。

| 问题 | 触发条件及影响 |
| --- | --- |
| 空根不重试 | `root == null` 直接返回，只能等待下一次事件；窗口切换期间容易错过 |
| 持续事件不断推迟扫描 | 每次事件都取消任务，再延后 650ms；若事件持续密集，首扫可一直被推后 |
| 响铃回调仅重置会话 | `RINGING` 会清除待执行任务，却没有主动重新安排扫描；若无后续事件，就不再采集 |
| 界面降级门槛过严 | 电话状态不可用时，要求事件文本有“来电/接听”等词，且包名或类名也符合；窗口内容变更事件的文本不一定完整 |
| 尝试次数按会话累计 | 失败后没有在每个新候选事件中恢复完整重试预算；“每个事件都重试两次”并不成立 |

建议用有截止时间的采集会话，响铃主动触发，事件负责唤醒或补充，有节制地重扫；空根与节点未就绪都进入同一重试机制。

### 4.8 已确认：节点结构被丢弃，人数拆成多个节点时无法识别

位置：服务第 130–146、222–224 行；解析器第 70–78 行。

采集阶段把所有节点扁平化成 `LinkedHashSet<String>`，丢失视图 ID、窗口、位置和父子关系；解析器逐行找人数，不会关联相邻节点。

本次模拟 `16` 与 `人标记` 分属两个节点，得到 `markCount=null`。如果手机恰好这样提供节点，肉眼看到连续文字也无济于事。正确做法是结合真实节点结构进行局部拼接，不能任意拼接全屏数字。

另外，当前限制深度 30、文本 80 条、每条 200 字；函数名叫 `collectVisibleText`，却没有检查 `isVisibleToUser`。文本过多、不可见旧内容或较深节点都可能干扰结果，但本次没有证据表明确实触及这些限制。

### 4.9 已确认：页面把“未读到”显示为“无”，容易误导排查

位置：`MainActivity.kt` 第 196–215 行；`CaptureRepository.kt` 第 36–54 行。

`markCount == null` 被显示成 `无`，实际含义可能是“悬浮卡片未展示”“节点未暴露”“尚未加载”或“解析失败”。建议显示“未知/未读取到”，并区分本次会话状态和历史最后一条记录。

“运行解析测试”按钮只解析硬编码的 `138 0013 8000 / 被23人标记 / 疑似诈骗` 并弹窗，不调用真实窗口采集，也不直接保存最近记录。它通过不能证明服务正常读取电话界面，当前硬编码样本也不能解释 `12123`。

## 5. 仍需真机确认的因素

### 5.1 系统窗口是否向该服务暴露节点

部分界面可能使用自绘文字、合并语义节点或敏感数据限制。Android 14 起提供 `accessibilityDataSensitive` 相关机制，节点访问可能受服务属性约束，但本次没有目标机节点证据，不能断言来电界面使用了这一机制。[Android View 官方说明](https://developer.android.com/reference/android/view/View#ACCESSIBILITY_DATA_SENSITIVE_YES)。

不能把设置 `isAccessibilityTool=true` 当成通用修复开关；该属性有特定用途，应先确认节点缺失原因及服务实际用途。也没有依据把这次故障直接归为截图安全标志、后台省电或某个手机品牌的限制。

### 5.2 电话状态和 SIM 卡订阅是否对应

服务第 172–174 行用默认 `TelephonyManager` 注册监听，没有按活跃订阅分别注册。官方说明该回调只对应所注册的订阅；未调用 `createForSubscriptionId()` 时使用默认订阅。双卡场景应核对实际响铃卡与监听订阅。[CallStateListener 官方说明](https://developer.android.com/reference/android/telephony/TelephonyCallback.CallStateListener)。

截图中 SIM 标识“1”不足以证明存在订阅错配，也不能证明电话状态权限已授权。该回调仅提供状态，不能直接提供标记人数、标记类型或替代窗口解析。

### 5.3 手机上运行的版本是否就是当前源码

工作区存在 APK 文件，但本次没有连接设备，未核对已安装 APK 与源码构建的一致性。所有代码结论针对当前源码；若手机使用了另一版 APK，需先确认安装版本及构建来源。

## 7. 建议的修复顺序与验收

本节是后续修复方案，本次未实施。

1. **先定位正确窗口。** 根据真实设备的事件与窗口清单识别来电窗口，结合事件窗口 ID、根包名、窗口类型/层级和来电控件特征选择候选。排除采集助手自己的节点。逐窗口解析，不把所有窗口文字盲目合并。
2. **收紧解析来源与兜底。** 优先从可信来电区域提取号码；区分 SIM 序号、旧记录、日期、人数。短号码保留支持，但要求有可靠上下文。类型使用已知标签或明确的“标记为/类型”等结构，不再任意删除“标记”后取剩余字符串。
3. **修正采集时序。** 响铃建立会话并触发扫描，空根重试，密集事件不能无限延期。以单次来电为边界保留候选字段，允许人数稍后补全；会话截止时落盘，若需要后续更新则使用同一记录 ID 和幂等更新约定。
4. **补足诊断和页面语义。** 记录实际内容来源、窗口、原始文字及选中原因；人数未知与明确为零分别显示；当前会话失败不伪装成旧记录成功。
5. **再做机型适配。** 根据实际节点 ID、布局和双卡订阅适配。只有确认目标文字没有向服务暴露后，才讨论其他可用数据渠道；OCR 是独立的截图识别方案，不能假定当前实现已有该能力或必定可用。

| 场景 | 修复后验收标准 |
| --- | --- |
| 例图1全屏来电 | 若四项文字向服务暴露，应得到 `076921738692 / true / 16 / 广告推销` |
| 例图2悬浮卡片 | 应识别可信卡片中的号码和类型；人数未暴露且未从同会话读到时保留未知 |
| 助手页面含旧号码 | 不把 `12123` 或应用标题作为新的来电记录 |
| 人数延迟出现 | 能补全同一来电记录，不因先识别类型而永久丢失人数 |
| 人数拆分节点 | 根据目标来电区域结构识别 `16 + 人标记`，避免跨区域拼接 |
| SIM 序号与号码邻接 | 不产生 `1076921738692` 这种序号污染结果 |
| 空根、密集事件、双卡 | 无永久饥饿或无后续事件即停扫；卡1/卡2各自验证 |
| 同号码再次来电 | 上一通结束后可建立新记录；同一通重复事件不会重复创建 |

### 8.2 建议后续添加的诊断字段
