# 来电按次采集、上传与历史记录：修复实现说明

日期：2026-09-29。工程：`来电标记采集助手_Kotlin_Android14-16_完整项目/CallMarkCollector`。

本次已修改源码。按用户要求，没有运行 Gradle、编译 Android App、打包、安装或替换 APK。项目中现有 APK 仍是修复前的版本。

## 1. 实现后的完整流程

1. 用户授权电话状态权限，并开启无障碍服务，首页保存完整 POST 接口地址。
2. 电话状态从非响铃进入响铃，立即创建一个带 UUID 的本地历史记录，显示“正在采集”。
3. 服务主动发起扫描，遍历可交互窗口，选择电话应用窗口或 SystemUI 中的来电卡片，排除自身应用。
4. 同一次来电最多补读 8 秒，间隔约 600ms，合并同号码的类型、人数与文字。重复窗口事件只唤醒扫描，不取消已有定时任务。
5. 8 秒到期，或用户接听/拒接/对方挂断使响铃结束时，完成同一条记录，先保存最终字段，再进入上传队列。
6. 队列按 recordId 原子领取任务，仅自动提交一次，并将成功、HTTP 错误、网络异常或未配置状态更新回这条记录。
7. 首页“查看来电历史记录”打开分页列表，点击记录查看详情和原始文字。可删除单条、清空记录，或手动重试失败上传。

“响铃一次”指一通电话的一个响铃阶段，同一通电话反复发出的铃声和窗口事件不会重复建记录。内部多次读取是为了等待页面加载和人数补全，最终仍是一条记录、一次自动提交。下一次独立响铃即使号码相同，也创建新的记录。

## 2. 本次修复的关键问题

| 修复前问题 | 当前实现 |
| --- | --- |
| 只读取当前活动窗口，可能读到助手页面 | 遍历 windows，活动根仅作补充；按实际根包名筛选，SystemUI 优先使用局部来电卡片 |
| 只过滤自身事件，扫描时未过滤自身根 | 根节点及遍历节点均排除本应用；解析器另有自身标题/历史文案防护 |
| 标题被误判为标记类型 | 去掉任意删除“标记”后的兜底；仅接受已知标签或明确类型句式 |
| 短号码、旧记录、SIM 序号污染号码 | 过滤自身记录文本、日期和人数行；常见完整号码优先；去除符合结构的 SIM 前缀 |
| 类型先出现就立即上传，人数无法补全 | 在有界采集期内合并同号码信息，期满再定稿 |
| 空根不重试、事件密集导致首扫延期 | 主动周期扫描，空根继续尝试；新事件不会不断重置已有任务 |
| 电话状态回调重置并取消任务 | 单独的 RingGate 识别响铃开始/结束，开始即主动扫描 |
| 只监听默认 SIM | 为所有可取得的活跃订阅注册回调，并等待各订阅初始状态，避免另一张空闲卡关闭恢复中的会话 |
| 最后一条记录被后续上传回调覆盖 | SQLite 按 recordId 更新；同一个进程内串行化记录变更 |
| 不支持历史和删除 | SQLite 持久历史，50 条分页，详情、单条删除、清空 |
| null 显示成“无” | 是否标记、人数、类型缺失均显示未知，明确零人数仍显示 0 |

人数局部拼接只在相邻直接兄弟节点分别为数字与“人标记”等结构、位置接近时进行，避免拼接全屏无关数字。窗口筛选仍依赖目标设备实际暴露的来电语义，不能凭截图保证所有 ROM 均可读取。

## 3. 本地记录与上传状态

数据库为应用私有目录的 `call_history.db`，包含：

- `records`：记录 ID、响铃时间、完整 JSON。按时间倒序查询，按 ID 更新和删除。
- `metadata`：当前响铃会话 ID、开始时间、是否完成，避免服务重连时简单重复建记录。

首次打开数据库时，将旧 SharedPreferences 的 last_record 迁移为 LEGACY 历史记录；迁移提交后移除旧副本。旧版记录可能包含此前误识别内容，因此不自动重新上传。

主要采集状态：

| 状态 | 页面含义 |
| --- | --- |
| SCANNING | 正在采集、等待文字补全 |
| CAPTURED | 已读取可信号码；标记字段可能仍未知 |
| NO_NUMBER | 本次响铃已尝试扫描，但没有读到可信号码 |
| LEGACY | 旧版迁移记录 |

主要上传状态：

| 状态 | 含义 |
| --- | --- |
| WAITING_CAPTURE | 尚未完成采集，不发送 |
| PENDING | 已保存最终结果，等待领取 |
| UPLOADING | 已领取，正在发出请求 |
| SUCCESS | HTTP 2xx |
| FAILED | HTTP 非 2xx 或网络异常 |
| UNCONFIGURED | 没有配置接口 |
| INTERRUPTED | 上次进程退出时仍在上传，送达情况未知 |

失败、未配置、中断记录允许在详情中手动重试。重试沿用 recordId 和 Idempotency-Key，需要服务端按该键去重，避免超时后重试重复入库。

未能读取号码也会保存并尝试上传 NO_NUMBER 记录，相关字段为 null。这样每次观察到的响铃都有结果，不会拿旧号码填充。服务端必须接受该结构，具体见工程内《服务端接口约定.md》。

## 4. 删除行为

- 删除单条或清空后立即从本地列表移除，首页最近记录同步刷新。
- 正在采集的记录被删除后，本次响铃仍保留去重标识；后续采集不会重新插入，也不会继续为它发出新的上传。
- 处于队列中且尚未领取/发送的已删除记录会跳过。
- 已经发送的请求无法撤回；迟到的成功或失败响应只执行按 ID 更新，不会恢复已删除的行。
- 本地删除不等于删除服务器数据，当前项目没有远程删除 API。

## 8. 明确边界

要以电话状态可靠区分一次响铃，必须授权 READ_PHONE_STATE。已取消仅凭界面“来电”二字创建会话的旧降级路径，防止查看通话记录也生成采集。

当前按设备整体“有电话正在响铃”的阶段建会话，支持不同 SIM 先后独立来电。两张 SIM 同时重叠响铃时，无障碍窗口本身不一定提供可绑定的订阅信息，当前不能保证为每张卡分别识别一条；该场景需要目标机节点适配。服务关闭、权限撤销或进程不运行期间发生且结束的电话，也无法事后补采。服务重连可恢复已保存会话，但无法从单个状态快照重建停机期间所有来电边界。

窗口可见不代表节点一定向该服务公开；不公开时只能记录缺失原因，不能编造号码或人数。本次未配置真实服务器，上传功能是否与目标接口兼容需按接口约定联调。

## 9. 历史列表补充标记信息（2026-09-30）

问题原因：采集模型已将 `isMarked`、`markCount` 写入记录 JSON，历史查询也会返回完整记录；首页及历史详情已有展示，但 `RecordFormatter.summary()` 只拼接时间、号码、采集状态、标记类型和上传状态，导致历史列表看不到是否标记和标记人数。

本次在每条历史摘要中增加“是否标记”和“标记人数”，与详情共用是否标记的格式化逻辑，直接显示该条历史记录保存的数据，不读取首页最新一通来电的数据。保留原有时间、号码、类型及上传提示。

- `isMarked=true/false` 分别显示“是/否”；字段缺失或为 null 时显示未知。
- `markCount=0` 如实显示 0；字段缺失或为 null 时显示“未知（未读取到）”，不猜测人数。
- 不修改数据库结构，不清空历史；旧记录中已经保存的字段在使用更新后的应用打开历史时直接显示。旧记录未采集到的字段仍显示未知。
