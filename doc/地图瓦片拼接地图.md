>
> 更新时间：2026-09-10
>
> 页面：`http://127.0.0.1:8085/waterlog-dia-bus`
>
> 当前状态：完成现状审查、公开数据源选型与开发实施设计；本文档本次只更新方案，尚未下载数据或实施第二版代码。

## 1. 第二版目标

在第一版“离线瓦片 + 两江业务河道 + Canvas 粒子”的基础上，将左侧地图调整为例图中的深蓝水系专题图风格：

1. 陆地区域以不同深度的蓝色块面表达，避免当前底图过亮或细节杂乱；
2. 行政区边界和区县名称低亮显示，形成清晰但不抢眼的地理参照；
3. 普通河网使用细蓝线铺底，嘉陵江和长江作为业务主河道加粗、高亮并保持流动效果；
4. 河道高亮段使用蓝白相间的流带，粒子沿河道方向运动；
5. 地图右下角增加“粒子动画”本地开关，用户可以暂停或恢复动画；
6. 继续离线运行，不访问高德服务器、不增加后端接口，不改动右侧水位输入、预警计算和弹窗事件协议。

第二版不是替换 Leaflet，而是在现有 Leaflet 地图上重新组织底图、行政区、区域河网、业务河道、粒子和站点的层级。

### 2.3 与目标例图的关键差距

对瓦片原图抽样检查后发现，现有 z10 JPEG 主要包含白色背景、区县/乡镇文字以及少量极细水系符号，没有例图中完整的行政区块面、行政边界和密集河网。

因此存在一个明确边界：

> 仅调整 117 张 JPEG 的 CSS `filter`，可以把白色底图变成深蓝色，但不能生成原图中不存在的行政区边界和区域河网，也不能可靠地把文字、道路、水系分别着色。

要接近例图，第二版必须采用“现有瓦片负责地名 + 本地 GeoJSON 补充行政区和区域河网 + 现有 RIVERS 负责业务主河道”的混合方案。若暂时没有 GeoJSON，只能完成 V2-Lite 深色调色，不能把它描述为完整例图效果。

### 4.2 公开数据源选型结论

本项目采用“公开源只在开发期下载，处理后的 GeoJSON 随前端包本地发布”的方式。浏览器运行时不访问 GitHub、Geofabrik、OpenStreetMap 或任何在线地图接口。

| 数据 | 采用来源 | 许可证/署名 | 选型结论 |
| --- | --- | --- | --- |
| 行政区边界 | [Supeset/China-GeoData](https://github.com/Supeset/China-GeoData) 的 `china_province_city_full.geojson` | 仓库声明 MIT License；项目内保留许可证与来源 | **主来源**。直接提供 GeoJSON、中文 `name`、`adcode`，可筛出重庆 38 个区县 |
| 行政区备选 | [geoBoundaries API](https://www.geoboundaries.org/api.html) 的 `gbOpen/CHN/ADM2` | `gbOpen` 总体按 CC BY 4.0 提供，但仍应核对下载文件元数据 | **仅备选**。名称多为拼音，且本项目无需同时混用两套边界 |
| 河网 | [Geofabrik 中国分区 OSM PBF](https://download.geofabrik.de/asia/china.html) | OpenStreetMap 数据采用 ODbL 1.0，必须显示 `© OpenStreetMap contributors` 并链接许可说明 | **主来源**。覆盖面和河网密度满足背景水系需求，可按 `waterway` 标签提取 |

不使用 Natural Earth 河流数据作为本次主来源：其比例尺更适合全国或全球概览，无法提供例图所需的重庆及周边密集支流。也不直接调用 Overpass API：范围较大时容易超时，且不符合本项目离线、可复现的工程目标。

### 4.4 区域河网 GeoJSON 落地

#### 4.4.1 下载范围

现有瓦片边界约为 `[105.1171875, 28.613459, 109.6875, 31.353637]`，不仅覆盖重庆，也触及四川、贵州、湖北和湖南。因此下载五个较小的 Geofabrik 中国分区，而不是下载约 1.5 GB 的全国 PBF：

```text
https://download.geofabrik.de/asia/china/chongqing-latest.osm.pbf
https://download.geofabrik.de/asia/china/sichuan-latest.osm.pbf
https://download.geofabrik.de/asia/china/guizhou-latest.osm.pbf
https://download.geofabrik.de/asia/china/hubei-latest.osm.pbf
https://download.geofabrik.de/asia/china/hunan-latest.osm.pbf
```

`latest` 会更新，因此它只用于开发期取数；每次下载后必须把响应时间、文件大小和 SHA-256 固定到 `scripts/map-sources.lock.json`。需要完全复现某次构建时，应使用 lock 中记录的日期归档文件，而不是重新使用 `latest`。

开发期下载命令：

```powershell
$mapSourceDir = 'scripts/map-source'
New-Item -ItemType Directory -Force -Path $mapSourceDir | Out-Null

$osmRegions = 'chongqing', 'sichuan', 'guizhou', 'hubei', 'hunan'
foreach ($region in $osmRegions) {
  $url = "https://download.geofabrik.de/asia/china/$region-latest.osm.pbf"
  $output = Join-Path $mapSourceDir "$region-latest.osm.pbf"
  Invoke-WebRequest -Uri $url -OutFile $output
  Get-FileHash -Algorithm SHA256 -LiteralPath $output
}
```

#### 4.4.2 Osmium 提取命令

开发机安装 `osmium-tool` 后，按 [Osmium 官方命令说明](https://docs.osmcode.org/osmium/latest/) 对每个分区分别裁剪和导出：

```powershell
$mapSourceDir = 'scripts/map-source'
$osmRegions = 'chongqing', 'sichuan', 'guizhou', 'hubei', 'hunan'

foreach ($region in $osmRegions) {
  $sourcePbf = Join-Path $mapSourceDir "$region-latest.osm.pbf"
  $clippedPbf = Join-Path $mapSourceDir "$region-clipped.osm.pbf"
  $waterwayPbf = Join-Path $mapSourceDir "$region-waterways.osm.pbf"
  $waterwayGeoJson = Join-Path $mapSourceDir "$region-waterways.raw.geojson"

  osmium extract -b 105.1171875,28.613459,109.6875,31.353637 $sourcePbf -o $clippedPbf --overwrite
  if ($LASTEXITCODE -ne 0) { throw "裁剪失败：$region" }

  osmium tags-filter $clippedPbf w/waterway=river,stream,canal -o $waterwayPbf --overwrite
  if ($LASTEXITCODE -ne 0) { throw "河网筛选失败：$region" }

  osmium export $waterwayPbf -f geojson --geometry-types=linestring --add-unique-id=type_id --show-errors -o $waterwayGeoJson --overwrite
  if ($LASTEXITCODE -ne 0) { throw "GeoJSON 导出失败：$region" }
}

node scripts/build-waterlog-map-data.mjs
if ($LASTEXITCODE -ne 0) { throw '地图数据预处理失败' }
```

不先对五个 `latest` PBF 执行 `osmium merge`：各分区快照时间可能略有差异，跨省边界也可能包含重复 OSM 对象。预处理脚本读取五份 GeoJSON 后按 Osmium 生成的 `Feature.id`（如 `w123456`）去重，再做几何裁剪与拼接，结果更容易审计和复现。

第一版只纳入 `river`、`stream`、`canal`，排除 `ditch`、`drain`、`dam` 等不适合作为大屏背景河网的要素。Feature 属性统一为：

```ts
type RiverFeatureProps = {
  name?: string
  nameZh?: string
  osmId: string
  osmWaterway: 'river' | 'stream' | 'canal'
  rank: 1 | 2 | 3
  direction?: 1 | -1
  business: boolean
}
```

等级映射为 `river → rank 1`、`canal → rank 2`、`stream → rank 3`。普通河网只做静态底层，不创建独立粒子；与 `flood-data.ts` 中嘉陵江、长江重叠的 OSM 线要么删除，要么标记 `business=true` 并在底层隐藏，避免双线叠加。

最终输出：

`src/package/BZAQ/BzWaterKpiDia/components/map-data/waterlog-rivers.gcj02.geojson`

### 4.5 坐标系统一与校准

Geofabrik 的 [GIS 数据格式说明](https://download.geofabrik.de/osm-data-in-gis-formats-free.pdf) 明确其坐标为 WGS84，经纬度顺序为 `[lng, lat]`；现有底图来自高德瓦片，其可视地物基准通常为 GCJ-02。若直接叠加 WGS84 河网，会产生数百米级错位风险，因此本项目最终显示数据统一到与现有瓦片一致的坐标基准：

1. OSM 河网输入固定标记为 `sourceCrs=WGS84`，先按 WGS84 范围裁剪，再执行一次 `WGS84 → GCJ-02`；
2. China-GeoData 仓库没有在数据说明中明确标注该文件坐标系，不能先验假定。预处理配置必须为行政区设置显式 `sourceCrs`，先用朝天门、嘉陵江与长江汇合口、区县边界拐点等控制点判断它与现有瓦片是否已经对齐；
3. 若行政区数据已经与高德瓦片对齐，记录 `sourceCrs=GCJ-02` 并跳过转换；只有核验为 WGS84 时才执行一次转换，禁止“看起来偏一点”就二次转换；
4. 输出文件名明确使用 `.gcj02.geojson`，并在第三方数据说明中注明“这是面向高德瓦片显示的工程坐标，不是标准 RFC 7946 WGS84 交换文件”；
5. 现有 `STATIONS` 和 `RIVERS` 如果已经与瓦片吻合则不重复转换；若不吻合，只在统一的数据入口转换一次，禁止 CSS 平移或逐图层手工补偿。

坐标转换必须写成纯函数并带测试样例，不能在 Leaflet 渲染循环中逐帧计算。

### 4.7 数据预处理脚本

计划新增：

`scripts/build-waterlog-map-data.mjs`

职责：

1. 校验输入是合法 `FeatureCollection`，经纬度未颠倒；
2. 从行政区文件筛出 `adcode` 以 `50` 开头的重庆区县，并与瓦片边界相交裁剪；
3. 清理 OSM 重复线、空几何和无效坐标，标准化 `name`、`nameZh`、`osmId`、`rank`；
4. 通过项目已有 `@turf/turf` 做裁剪和简化，行政区初始容差建议 `0.002`，河网建议 `0.0006–0.001`，最终以视觉和文件大小验收为准；
5. 对待显示坐标统一执行一次 WGS84 到 GCJ-02 转换；
6. 排除或标记与业务嘉陵江、长江重复的河段；
7. 输出 `waterlog-admin.gcj02.geojson`、`waterlog-rivers.gcj02.geojson`；
8. 输出输入/输出要素数、坐标点数、文件大小、来源哈希和转换状态，构建失败时返回非零退出码。

原始 PBF 和全国行政区文件只放在已加入 `.gitignore` 的 `scripts/map-source/`，不进入 Webpack 依赖图，也不提交到仓库。项目仅提交处理后的两份 GeoJSON、来源锁文件和第三方数据说明。代码中优先引用 Turf 的具体子包，避免把整个 Turf 聚合包重复打入页面。

## 5. 地图视觉实现

### 5.1 离线瓦片深蓝化

当前 `.waterlog-offline-tile` 已使用 `invert / sepia / saturate / hue-rotate / brightness / contrast`。第二版继续采用非破坏式调色，但降低瓦片存在感：

- 整体底色统一为深海军蓝；
- 地名保留为灰蓝色，不做高亮白字；
- 道路和乡镇细节降低对比度；
- 瓦片透明度控制在 `0.62–0.76`，由行政块面提供主体颜色；
- `.water-grid` 透明度从当前约 `0.22` 降至 `0.08–0.12`，避免网格破坏例图中的连续地图质感。

具体滤镜值需要以浏览器截图迭代，不能只根据单张瓦片颜色写死。必须同时检查区县文字、河道、站点三者的可读性。

### 5.2 行政区和文字

行政区 Polygon 使用 Canvas renderer 绘制填充与边界，避免大量 SVG DOM 节点。区县名称优先保留瓦片文字；只有瓦片缺少关键区县名称时，才从 GeoJSON `center/centroid` 添加 `L.divIcon`，防止同一个地名重复出现。

标签规范：

- 区县：12–14px，`#a9b9c9`，透明度 `0.72`；
- 乡镇：10–11px，`#8297ab`，透明度 `0.58`；
- 站点：继续使用当前白底业务标签，不与底图标签合并。

### 5.3 区域河网

普通河网通过一个 `L.geoJSON` 图层和共享 Canvas renderer 绘制：

| 河网等级 | 颜色 | 线宽 | 透明度 |
| --- | --- | --- | --- |
| rank 1 | `#169ff2` | 2.0px | 0.90 |
| rank 2 | `#0b8de5` | 1.2px | 0.78 |
| rank 3 | `#0875c8` | 0.7px | 0.60 |

区域河网不使用发光滤镜和逐条动画，避免数百条河道同时运动造成性能下降。其作用是形成例图中的密集蓝色水系背景。

### 5.4 嘉陵江和长江主河道

继续使用 `flood-data.ts` 中 `RIVERS.jialing`、`RIVERS.yangtze`，保留当前五层结构：glow、bank、body、current、spark。

第二版视觉调整：

- 外层水体使用 `#27aaf5`，内层高光使用 `#d9f8ff`；
- 主体线宽提高到普通河网的 3–4 倍；
- `river-current` 使用蓝白相间长短虚线，模拟例图中的亮段流动；
- 保留嘉陵江与长江不同动画周期，避免机械同步；
- 当前长江橙色仅在业务图例或预警路径需要区分时保留，普通态优先采用统一蓝色水系风格；
- 告警发生后仍由 `LEVEL_COLOR` 控制告警路径，不能被底图样式覆盖。

### 5.5 粒子动画开关

在地图右下角新增本地开关，视觉参考例图但保持项目现有蓝色大屏语言：

```text
[开关] 粒子动画
```

实现状态：

```ts
const particleEnabled = ref(true)
```

行为要求：

- 关闭后取消或跳过 Canvas 粒子绘制，清空粒子画布；
- 河道 SVG 流带可以继续保留，保证地图不是完全静止；
- 再次开启后从当前时间恢复，不创建第二个 `requestAnimationFrame` 循环；
- `prefers-reduced-motion: reduce` 的优先级高于开关；
- 状态仅保存在当前弹窗实例，不增加接口和 LocalStorage。

## 7. 分阶段实施顺序

### 阶段一：V2-Lite 底图调色

1. 建立 Pane 层级；
2. 调整瓦片透明度、滤镜、暗角和网格；
3. 优化站点与 HUD 的视觉优先级；
4. 增加粒子动画开关。

该阶段不依赖新增 GeoJSON，可以立即实施，但效果只会接近“深蓝专题图”，不会出现例图中的完整行政区和密集水系。

### 阶段二：行政区专题底图

1. 从固定提交下载 China-GeoData 行政区 GeoJSON，并核对 SHA-256；
2. 筛选重庆区县，裁剪、简化、坐标统一并输出本地资源；
3. 加入行政填充和边界；
4. 处理瓦片标签与自定义标签的重复问题。

### 阶段三：区域河网强化

1. 下载五个 Geofabrik 分区 PBF，锁定下载时间和 SHA-256；
2. 用 Osmium 对各分区分别裁剪、筛选 `waterway`，再由预处理脚本按 OSM ID 合并去重并生成 `rank`；
3. 使用 Canvas renderer 绘制静态支流；
4. 将嘉陵江、长江 SVG 动画置于河网之上；
5. 校验所有站点与主河道空间位置；
6. 根据浏览器性能调整简化精度和支流显示等级。

### 阶段四：视觉与性能收口

1. 在 500px、900px、1400px 三类地图宽度下截图对比；
2. 校正文字、河线、站点的对比度；
3. 检查缩放、拖动、弹窗缩放后的同步；
4. 检查粒子开关、关闭弹窗和重新打开时是否存在重复动画或内存泄漏。

## 8. 验收标准

### 8.1 数据与构建

1. 117 张离线瓦片继续通过 `require.context` 打包，Network 中不访问高德或其他地图服务；
2. 原始 GeoJSON/PBF 的来源、SHA-256、许可证、裁剪范围和坐标转换均可由 lock 文件追溯；
3. 输出 GeoJSON 范围位于瓦片边界内，经纬度没有颠倒，并已与高德瓦片视觉坐标对齐；
4. 页面持续显示 OpenStreetMap 署名及 ODbL 许可入口；
5. Vue SFC、TypeScript、SCSS 和 Webpack 编译通过；
6. `git diff --check` 通过；
7. 页面未新增后端请求和运行时外部数据请求。

### 8.2 视觉

1. 地图主体为连续深蓝色块面，不出现白色瓦片或明显拼接缝；
2. 行政边界可见但弱于河网，行政名称可读但弱于站点名称；
3. 普通河网连续、方向正确，主河道明显高于支流；
4. 嘉陵江、长江高亮段和粒子沿真实折线运动，不穿越河道拐点；
5. 地图缩放和拖动后，瓦片、行政区、河网、业务河道、粒子和站点不发生错位；
6. 右下角粒子开关不遮挡图例、站点或右侧表单。

### 8.3 功能回归

1. 点击站点、填写水位、重置和“计算预警”保持原有行为；
2. 无预警和有预警状态的告警结果动画正常；
3. 告警路径颜色和到达时间不受地图主题影响；
4. 关闭粒子后 CPU/GPU 占用下降，重新开启只存在一个动画循环；
5. 组件卸载后 Leaflet、ResizeObserver、定时器和动画帧全部释放。

## 9. 风险与决策

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 仅有 z10 瓦片 | 放大后文字和线条发虚 | 限制有效缩放；后续补充 z11–z13，不无限放大 z10 |
| 当前瓦片缺少行政边界和密集河网 | 仅靠滤镜无法复刻例图 | 将本地行政区、河网 GeoJSON 作为完整 V2 的前置数据 |
| GeoJSON 点数过多 | 首屏慢、拖动卡顿 | 构建前裁剪和简化；普通河网使用共享 Canvas renderer |
| 普通河网全部动画 | 动画节点过多 | 只动画嘉陵江、长江和必要告警路径 |
| 标签重复 | 地名重叠 | 瓦片标签优先，自定义标签只补缺失项 |
| 统一蓝色后业务河流区分下降 | 图例语义变弱 | 普通态蓝色统一，告警/选中态恢复业务色和高亮 |
| OSM 河网为 WGS84、高德瓦片为 GCJ-02 | 河线与底图错位 | 预处理阶段统一转换一次，并用控制点验收；禁止重复转换 |
| `latest` 河网数据持续变化 | 构建不可复现 | 记录真实下载时间、归档 URL 与 SHA-256 到 lock 文件 |
| 第三方数据许可或行政区调整 | 对外发布存在合规风险 | 随包保留来源/许可，页面显示 OSM 署名，生产发布前复核行政区版本 |

## 10. 第二版实施结论

推荐采用“离线瓦片标签层 + China-GeoData 行政区 GeoJSON + Geofabrik/OpenStreetMap 河网 + 现有两江动画层”的组合方案。这是当前工程中最接近例图、同时保持离线运行和业务逻辑稳定的实现路径。

数据来源现已明确，可以直接进入工程实施：先按固定提交取得行政区文件，再下载并锁定五个 OSM 分区快照，由预处理脚本生成两份 `.gcj02.geojson` 本地资源。完整第二版不在运行时访问外部服务，也不通过放大、滤镜或手动画线伪造真实区域河网。
