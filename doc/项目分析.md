# 中晟辉业务台账项目结构与 appid 问题分析

分析日期：2026-10-02。分析范围为本项目当前目录内全部 17 个原有文件（含隐藏文件检查），不包含上级目录的其他项目，也不包含云端实际资源。本文是新增分析文档，未修改业务代码、云端配置或数据。

后续记录：本文保留首次分析时的结构及行号。随后已按普通网页架构修改到账记录与预警台账，当前变更及验证结果见同目录《功能修改说明.md》。

## 1. 核心结论

**当前目录是“原生 HTML/CSS/JavaScript 网页 + uniCloud 阿里云后端”的交付包，不是可以直接按标准 uni-app 工程运行、编译的完整项目。**

关于“是否缺少源码”，需要分开判断：

| 问题 | 判断 | 依据 |
| --- | --- | --- |
| 前端业务代码是否完全丢失？ | 没有。现有代码可阅读、可直接修改 | `dist/app.js` 有 1620 行业务代码、具名函数和中文注释；页面与样式也存在 |
| 后端是否只有接口地址、没有实现？ | 不是。云函数实现已经提供 | `uniCloud-aliyun/cloudfunctions/zsh-ledger-api/index.js` 有 558 行实现 |
| 是否缺少标准 uni-app 工程文件？ | 是，当前目录未提供这套工程 | 没有 `manifest.json`、`pages.json`、`App.vue`、`main.js`、`.vue` 页面，也没有 `src/manifest.json` |
| HBuilderX 能否从本目录读取 DCloud appid？ | 当前找不到对应配置 | 没有 manifest 文件；自有业务代码内也未发现 `appid` / `__UNI__` 标识 |
| 能否认定原作者遗漏了 Vue 源码？ | 不能 | 现有前端本身采用原生网页写法，没有证据证明曾经存在 Vue / uni-app 源工程 |
| 交付资料是否存在明确缺件？ | 是 | 页面和接口封装引用了部署说明，但 `uniCloud-aliyun/部署说明.md` 不存在 |
| 是否已经具备可复现的云端部署交付？ | 尚不能确认 | appid、部署工程、URL 化及跨域等配置未完整交付；未核验实际服务空间 |

**“关联阿里云空间提示缺少 appid”的首要原因，是本目录没有标准工程中的 `manifest.json` 和有效 DCloud 应用标识。不是在业务代码中随便补一个 appid，就能证明工程完整或云服务可用。**

上述定位由本地文件与官方工程要求相互印证；本次未操作 HBuilderX 重现弹窗，因此不能排除其版本、导入目录或账号权限还存在后续问题。

## 3. 技术架构与运行链路

### 3.1 前端是普通网页

`dist/index.html:368` 加载 JSZip，`dist/index.html:369` 用 `type="module"` 加载 `app.js`。`dist/app.js:1` 开始导入 PDF.js、云配置和接口模块，并直接使用 DOM、`localStorage`、IndexedDB、FileReader、Canvas 等浏览器能力。

没有发现 Vue 组件、Vue 挂载入口、uni-app 页面路由配置、Vite/Webpack 配置或前端 npm 构建脚本。现有网页可以由静态服务器直接提供，不依赖先执行 `npm install` / `npm run build`。

因此，目录名虽然叫 `dist`，但其中自有业务 JavaScript 并不是无法阅读的压缩包。它可以作为当前版本的维护入口。没有 `src/` 或 source map，不等于业务源码缺失；至于历史开发目录是否另有一份，需要原交付方提供证据。

### 3.2 前后端通过 HTTP 通信

```text
浏览器访问 dist/index.html
  → app.js 处理页面事件
  → cloud-api.js 使用 fetch POST
  → cloud-config.js 中的 apiBaseUrl
  → zsh-ledger-api 云函数解析 action
  → uniCloud 云数据库 / 云存储
  → 返回 JSON 或 PDF 内容
```

实际接口请求形式为：

```http
POST <配置的云函数 URL>
Content-Type: application/json
Authorization: Bearer <登录后取得的令牌>

{"action":"loadMeta"}
```

登录接口不要求已有令牌。其他业务由后端校验会话和角色。前端没有使用 `uniCloud.init()` 或 `uniCloud.callFunction()`，也没有向这些 HTTP 请求传入 DCloud appid。

这说明 **IDE 关联空间所需的应用标识，与网页现有的 HTTP 调用配置，是两个不同层面**。官方文档也说明非 uni-app 系统可以通过云函数 URL 化访问 uniCloud。[官方说明：云函数相关问题](https://doc.dcloud.net.cn/uniCloud/faq/cf.html)

### 3.3 本地启动脚本只提供网页

`server.ps1` 将 `dist` 作为站点根目录，监听 `127.0.0.1:8765`，按扩展名返回 HTML、JS、MJS、CSS、PDF 和 XLSX 文件；没有代理云接口，也没有实现本地数据库。

在项目根目录可使用以下命令启动网页：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\server.ps1 -NoBrowser
```

随后访问 `http://127.0.0.1:8765/`。本次只检查了脚本语法，未启动服务或验证浏览器流程。由于 `cloud-config.js` 当前设置 `enabled: true`，登录和业务操作仍然依赖配置的云端。不要把本地网页能打开理解为本地已有完整后端。

## 5. 后端与数据结构

### 5.1 云函数

只有一个业务云函数 `zsh-ledger-api`，通过 `body.action` 分派操作，包含：

- `login`、`logout`、`me`、`changePassword`、`listUsers`、`resetPassword`。
- `load`、`loadMeta`、`loadChunk`、`save`、`importProperties`。
- `uploadAttachment`、`getAttachmentUrl`、`getAttachmentContent`、`deleteAttachment`。

入口是 `exports.main`，代码采用 CommonJS。`package.json` 的 `dependencies` 为 `{}`；代码依赖 Node 内置 `crypto`、`http`、`https` 和云运行环境提供的 `uniCloud`。未发现引用但缺失的本地公共模块。因此，当前没有 `node_modules` 并不构成已证实的后端源码缺件。

云函数不能当普通独立 Node 服务直接启动：在文件第 6 行就使用 `uniCloud.database()`，需要平台环境。前端与后端的 action 名称经源码对照存在对应实现。

### 5.2 数据库与附件

| 资源 | 存储内容 | 结构特点 |
| --- | --- | --- |
| `zsh-ledger-users` | 用户名、角色、密码摘要/盐、改密标记、锁定时间 | 固定 `admin`、`operator1`、`operator2` 三个用户 ID |
| `zsh-ledger-sessions` | 用户 ID、创建时间、过期时间 | 文档 ID 为令牌 SHA-256 摘要；会话有效期在代码中设为 12 小时 |
| `zsh-ledger-state` | 项目、收款、物业设备和设置 | `user-<用户ID>` 保存个人数据；`shared-properties` 保存共享数据 |
| uniCloud 云存储 | PDF 附件 | `ledger-pdf/<用户ID>/...` 路径；前后端都设置 1 MiB 上传限制 |

三个 schema 都禁止客户端直接读写，业务通过云函数访问数据库。schema 是结构和权限声明，不是业务数据备份；`dist/sample` 也只是样例文件。

`ensureFixedUsers()` 会为缺失的固定用户创建账号，所以没有单独的账号初始化 JSON 并不能直接判为错误。但表结构、初始化步骤和原空间数据迁移仍需要部署说明。

### 5.3 缓存和同步

浏览器使用 `localStorage` 保存会话令牌和按账号划分的台账缓存，IndexedDB 保存附件。业务保存先更新本地状态，约 700 毫秒后触发云端保存；读取云端失败时会显示本机缓存。

后端带 `revision` 校验，版本冲突时返回 409。但实现是“先读取版本，再使用 `set()` 写入”，未见事务或原子条件更新。它可以检测部分冲突，不能直接当作严格的并发写保护。大数组按用户整份存入文档，分批读取只减少 HTTP 响应大小，没有改变底层文档存储粒度。

## 6. appid 缺失的定位

### 6.1 本地检查证据

本项目内未发现：

```text
manifest.json
src/manifest.json
pages.json
App.vue
main.js
src/
pages/
.hbuilderx/
根目录 package.json
```

自有业务代码中也没有 DCloud appid 配置。唯一 `package.json` 位于云函数目录，只声明包名、版本和入口，它不能替代应用的 manifest。

官方规定：HBuilderX 创建的 uni-app 工程将 `manifest.json` 放在根目录；CLI 创建的工程通常放在 `src` 内，`appid` 由 DCloud 分配。[官方说明：manifest.json 应用配置](https://uniapp.dcloud.io/collocation/manifest.html)

结合用户反馈，可作出高可信判断：当前目录没有提供 HBuilderX 关联流程要读取的应用身份配置。它虽然有 `uniCloud-aliyun` 文件夹，但这个文件夹本身不能代替应用工程。

### 6.2 appid、spaceId、接口 URL 不可混用

| 名称 | 含义 | 本项目情况 |
| --- | --- | --- |
| DCloud appid | DCloud 应用标识，常见形式为 `__UNI__...` | 未找到 |
| uniCloud spaceId | 云服务空间标识 | 需要从有权限的控制台确认，不能把域名中的片段当成完整交付依据 |
| 云函数 URL | 网页发送 HTTP 请求的地址 | `dist/cloud-config.js:3` 已配置一个具体地址 |
| 静态站点 URL | 网页托管地址 | `dist/cloud-config.js:4` 和云函数 `STATIC_SITE_URL` 有对应配置 |
| 微信等平台 appid | 对应平台分配的应用标识 | 与此次 DCloud 标识问题不是同一个配置项 |

不能将服务空间 ID、阿里云 AccessKey、云函数名称或网址填入 `manifest.json.appid`。已有 URL 也无法反推出原应用的 DCloud appid。[官方说明：DCloud appid](https://uniapp.dcloud.net.cn/dev/app/introduction.html)

### 6.3 不应采用的判断和处理

- 不应因为目录名为 `dist`，就断言“只有编译结果，所有源码丢失”。这里的业务逻辑是可读的普通 JavaScript。
- 不应为了消除弹窗，在 `cloud-config.js` 随意添加 `appid`；现有封装不会读取它，IDE 也不以该文件作为标准应用配置。
- 不应把虚构的 `__UNI__...` 写入 manifest。需要取得本人或协作账号有权限使用的真实应用标识。
- 只补一个 manifest，至多补上部分工程元数据，不能保证目录立即成为可编译的 uni-app 工程，也不能把 DOM 网页自动转换成小程序或原生 App。

## 7. 建议的补齐路径

### 7.1 优先确认原交付方是否有原工程

应索取或核对以下内容：

1. 原 HBuilderX 工程或用于部署云函数的管理工程，以及真实 `manifest.json`。
2. 原 DCloud appid、应用归属及协作权限；原阿里云服务空间的归属和访问权限。
3. 页面中明确引用但未交付的 `uniCloud-aliyun/部署说明.md`。
4. 云函数 URL 化路径、集成响应、跨域、运行环境、超时和静态托管配置。
5. 如需迁移已有业务：数据库备份、云存储附件及 fileID 迁移安排。

如果原工程确实存在，恢复该工程和原应用身份最便于保持版本及部署一致；不能只根据当前目录猜一个新 appid 作为原应用身份。

### 7.2 没有原工程时：保留网页，建立标准部署工程

对于当前“网页 + HTTP 云函数”架构，可以用一个由 HBuilderX 正式创建的 uni-app 工程承载云函数管理，不必为了关联空间而重写现有业务页面。建议步骤如下，本文仅给出方案，尚未执行：

1. 在当前项目内规划独立的部署工程目录，例如 `tools/unicloud-deploy/`，通过 HBuilderX 新建空白 uni-app 项目并启用阿里云 uniCloud。
2. 保留 HBuilderX 生成的 `manifest.json`、`pages.json`、`App.vue`、`main.js` 等模板文件，确认 manifest 中已经取得有效 DCloud appid。
3. 如已有需要继续使用的原应用，先确认原 appid 和授权；若为新的部署管理工程，则通过本人账号取得其真实 appid。不要将新 ID 描述为找回的原 ID。
4. 将现有 `uniCloud-aliyun/cloudfunctions/zsh-ledger-api` 及三个数据库 schema 放入这个工程对应的 uniCloud 目录。供应商目录名以 HBuilderX 实际生成结果为准，避免放错层级或同一供应商重复目录。
5. 导入并操作这个部署工程，在其 uniCloud 目录右键关联有权限访问的阿里云服务空间。不要只导入 `dist` 或把 `uniCloud-aliyun` 子目录当完整应用根目录。
6. 确认关联成功后，再按目标空间情况上传云函数和 schema。上传部署与初始化必须区分，已有业务空间不应被当作空白空间重新灌入数据。
7. 前端仍按静态网页部署 `dist` 内容。日后需确定一份云函数源码作为维护入口，避免原目录和部署目录长期存在不同版本。

官方快速上手给出了标准项目创建、获取 appid 和关联空间的流程；具体菜单名称以安装的 HBuilderX 版本为准。[官方说明：uniCloud 快速上手](https://doc.dcloud.net.cn/uniCloud/quickstart.html)

该方案解决的是“给云函数提供标准 IDE 部署入口”，没有自动实现 uni-app 跨端页面。如果后续目标是微信小程序或 Android App，需要另外评估 DOM、文件、PDF 和页面导航等能力的迁移范围。

### 7.3 关联成功后，还要核对网页调用配置

关联成功只说明 IDE 能定位目标空间，不代表网页已经切换到该空间。当前网页直接使用 `cloud-config.js` 的 URL，切换 IDE 关联不会自动替换它。

| 核对项 | 原因与处理位置 |
| --- | --- |
| 云函数 URL 化 | 当前前端走 HTTP，需取得目标空间实际可用的 `zsh-ledger-api` URL，更新 `dist/cloud-config.js` 的 `apiBaseUrl` |
| 集成响应 | 后端使用 `mpserverlessComposedResponse`、`statusCode`、`headers`、`body` 和 Base64 PDF 响应，需核对平台配置与实际返回行为 |
| 页面域名白名单 | 云函数 `index.js:15`、`:32` 固定检查原站点与本地来源；换站点时应同步核对 `STATIC_SITE_URL` |
| 浏览器跨域 | 普通 JSON/OPTIONS 响应本身没有完整 CORS 响应头；需确认平台是否提供跨域处理，覆盖 POST、OPTIONS、Content-Type 和 Authorization |
| 静态站点配置 | `cloud-config.js.staticSiteUrl` 目前仅见定义，未发现业务使用；只改它不会修改后端白名单，也不会自动发布网页 |
| 数据库和附件 | schema、真实台账和云存储文件分属不同资源；关联新空间不会迁移旧数据或重写附件 fileID |

集成响应格式可参照[官方说明：云函数 URL 化](https://doc.dcloud.net.cn/uniCloud/http)。当前项目的 JSON 和 PDF 请求都带有响应兼容代码，但不能用兼容代码的存在替代实际部署核验。
